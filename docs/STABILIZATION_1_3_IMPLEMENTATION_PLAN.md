## 1. 목표와 범위

우준이가 오늘 학습을 끝까지 진행하면 결과가 안전하게 저장되고 다음 활동으로 이동하며, 주간 약점을 정확한 문항으로 복습할 수 있게 한다.

이번 범위:
1. 하루 목표 시간, 과목 배정, 퀴즈 진입, 완료·저장 상태의 일관성.
2. 일요일 복습에서 공개된 모의고사 오답 우선 배정.
3. 수학 정답의 독립 검증, 독해 정답·오답 근거 검수, 실패 문항 처리.

범위 밖:
- 전체 UI 리디자인, 신규 과목·학년·지문 확장.
- Firestore 권한 구조나 서버 채점 아키텍처 교체.
- 기존 성적·최초 답안·오답 기록 일괄 수정/삭제.
- 유료 AI API 도입, 학습 중 실시간 AI 채점.
- 과거 기록을 새 정답으로 자동 재채점.

기존 크림색 UI를 유지한다. 상태 설명과 버튼만 필요한 만큼 조정한다.
시간은 계획용 예상치이며 아이의 실제 풀이 속도까지 30/45/60분으로 강제할 수 없다.

## 3. 공통 불변 조건

1. 학습자 ID·한국 날짜·계획 ID·과목·학습 범위를 모두 대조한다.
2. 정답률이 낮아도 유효한 퀴즈를 제출하고 저장하면 오늘 활동은 완료된다.
3. 점수/숙달과 활동 완료는 별도다. 힌트·복습·재시험을 최초 실력 점수로 섞지 않는다.
4. 브라우저에 답을 표시한 것과 영구 저장된 것을 구분한다.
5. 서버 전송 지연만으로 같은 기기에서 다음 활동을 막지 않는다.
6. 기기 저장 실패 시 완료라고 표시하지 않는다. 답안을 유지하고 재시도한다.
7. 완료 후 재클릭/새로고침/서버 재수신으로 보고서·시간·보상이 중복되지 않는다.
8. 다른 계정의 늦은 응답은 현재 화면과 저장소를 갱신하지 않는다.
9. 비공개 모의고사 문제·정오답·해설을 복습 대상으로 사용하지 않는다.
10. 모호하거나 잘못된 문항을 학생 오답으로 확정하지 않는다.
11. 기존 완료 기록을 새 정책 때문에 미완료로 되돌리지 않는다.
12. 테스트를 통과시키기 위해 증거 없이 정답·완료 조건을 느슨하게 하지 않는다.

## 4. 작업 A: 일일 시간과 완료 흐름

### A1. 시간 배분 단일 정책

신규 `learning-budget-policy.js`에 순수 정책을 둔다. 기존 전역 구조에 맞춰
`SmartStudy.LearningBudgetPolicy`로 노출한다. 새 프레임워크나 빌드는 도입하지 않는다.

| 과목 | 30분 | 45분 | 60분 |
|---|---:|---:|---:|
| 국어 독해 | 5 | 8 | 10 |
| 국어 어휘 | 4 | 6 | 8 |
| 영어 단어 | 3 | 4 | 5 |
| 영어 문법 | 3 | 4 | 5 |
| 영어 독해 | 5 | 7 | 10 |
| 수학 | 6 | 10 | 14 |
| 수학 공식 | 2 | 3 | 4 |
| 한자 | 2 | 3 | 4 |
| 합계 | **30** | **45** | **60** |

이는 학습+퀴즈의 예상 활동 시간이다. 과목별 시간 전체를 퀴즈 전 대기 시간으로 쓰지 않는다.
이번 변경에서는 문항 수나 모든 과목의 새 진도 양을 자동 축소하지 않는다.
따라서 UI는 “예상 45분”으로 표현하고 정확히 45분 안에 끝난다고 약속하지 않는다.

정책 함수 예:
```js
allocate(budgetMinutes) // [{subject, minutes}, ...] 8개, 합계 불변
validateConfiguration(settings) // {valid, conflicts: [...]} 시간 설정 충돌
```

- 관리자·오늘 학습·주간 표시가 같은 정책을 읽게 한다.
- `VOCAB_EXTRA_MINUTES` 소비처를 전수 검색해 폐기/호환 처리한다.
- 기본 4활동 생성 → 8활동 확장 중간 값이 화면/저장에 새어 나오지 않게 한다.
- `getPlan()` 조회마다 재생성되는 반복 갱신을 막는다.
- 계획 없는 날의 7개 기본값은 공통 과목 수 8로 바꾼다. 옛 계획 분모는 실제 task 수 유지.
- 수학 공식 시간이 수학 시간에도 들어가는지 회귀 테스트로 확인한다.

### A2. 퀴즈 진입 시간 정책

일일 시간 합계 수정만 하고 `study-timer.js`의 숨은 적응형 대기를 방치하지 않는다.

이번 구현의 정책:
- 오늘 학습 경로에서는 최근 낮은 점수에 따른 추가 5/10/15분 대기를 적용하지 않는다.
- 보호자가 명시적으로 설정한 최소 학습 시간은 보존한다.
- 자유 학습 경로의 기존 시간 정책은 변경하지 않는다.
- 점수가 낮은 경우 다음 추천/복습에서 보완하고, 이미 제출한 활동을 다시 잠그지 않는다.
- 일일 경로 판정은 URL 플래그만 믿지 않는다. 활성 사용자·오늘 계획·task·context를 검증한다.
- 일일/자유 학습 모두 실제 활동 시간은 계속 기록한다.

착수 시 `getBaseMinutes()`가 명시 설정과 기본값을 어떻게 구분하는지 확인하고 문서에 기록한다.
저장 형식으로 구분할 수 없다면 기존 값을 임의로 “기본값”이라 간주하여 없애지 않는다.
이 경우 호환 정책으로 기존 최소 시간을 유지하고, 관리자에서 적용 값을 명시적으로 선택할 수 있게 한다.

보호자 최소 시간과 배정 시간이 충돌할 때:
- 예: 영어 단어 배정 4분, 보호자 최소 10분.
- 관리자 저장 전에 충돌 과목과 두 숫자를 표시한다.
- “최소 시간 수정” 또는 “목표 시간 변경”으로 해결하도록 한다.
- 기존 충돌 설정은 삭제하지 않고 학습자에게 “보호자 설정으로 더 시간이 필요해요”와 실제 남은 시간을 표시한다.
- 충돌 해소 없이 “총 예상 45분”만 단독 표시하지 않는다. 예상 초과를 함께 표시한다.
- 학습자에게 보호자 설정을 우회하는 버튼을 제공하지 않는다.

타이머 진입 판단을 DOM의 `.stb-remain` 존재에 의존하지 말고 상태 API로 바꾼다.
상태에는 `unlocked`, `remainingSeconds`, `reason`, `source`를 포함한다.
DOM은 이 상태를 보여주는 역할만 맡긴다.

### A3. 완료 판정과 저장 상태 분리

영구 학습 상태와 동기화 상태를 한 문자열에 섞지 않는다.

| 축 | 상태 예 | 의미 |
|---|---|---|
| 활동 | ready / in_progress / completed | 오늘 활동 진행 |
| 제출 UI | editing / saving / saved / save_error | 기기 저장 과정 |
| 전송 UI | pending / syncing / synced / sync_error / unknown | 서버 전달 상태 |
| 채점 | graded / needs_review | 점수 확정 가능 여부 |

기존 보고서의 필드를 무조건 교체하지 않는다. 어댑터/순수 판정 함수로 기존 형식과 호환한다.
`LearningProgress.evidence`, `refreshEvidence`, `TodayJourney.state`의 판정이 어긋나지 않게 공통 함수를 사용한다.

완료 증거:
- 소유 사용자·날짜·과목·범위 일치.
- 유효한 sessionId, 양의 문항 수, 제출된 전체 답안.
- draft가 아니고 기기 영구 저장 성공.
- 지정 과제는 정확한 지정 범위와 일치해야 함.
- 학습을 시작하지 않고 0문항을 제출한 기록은 인정하지 않음.
- 정상 채점 가능한 문항은 정오답 boolean을 유지.
- `needs_review`를 완료로 인정할 경우, 새 버전이 생성한 명시적 제출 상태·전체 응답·문항 원본·저장 성공이 모두 있어야 함.
- 옛 불완전 보고서에 `correct:null`이 있다는 이유만으로 완료를 인정하지 않음.
- “활동 제출 완료 · 채점 확인 중”은 가능하나 가짜 100점, 임의 정답, 점수 보상은 금지.

저장 순서:
1. 연속 클릭 잠금, 답안 snapshot 고정.
2. 기존 세션 ID로 보고서 저장.
3. `LocalRepository.flush()` 등 실제 durable 완료를 기다림.
4. 동일 계정·동일 제출인지 재확인.
5. 완료 증거 반영 후 다음 과목 버튼 노출.
6. 서버 전송은 기존 재시도 경로로 수행, 서버 확인 전 “동기화 완료” 표시는 금지.

`flush()` 오류 전달과 계정 전환 동작을 실제 구현에서 확인한다.
저장 API가 실패를 삼키면 해당 경계만 수정하고 저장 체계 전체를 재작성하지 않는다.

### A4. 기존 계획 전환

새 정책 버전은 `allocationPolicyVersion: 2` 등 독립 필드로 관리한다.
`curriculumVersion`은 기존 4→8활동 확장에 쓰이므로 의미를 확인하지 않고 2로 바꾸지 않는다.

- 과거 날짜: 읽기만, 변경 금지.
- 오늘 미시작: 새 배분 적용 가능. 기존 task ID와 선택 범위는 가능한 한 유지.
- 오늘 한 활동이라도 시작/제출: 배분·순서·선택 범위 동결, 다음 날부터 새 배분.
- 완료된 계획: 그대로 유지.
- 진행 중 보호자 변경: 다음 계획 적용 문구 표시. 기존 필수 범위를 몰래 교체하지 않음.
- 반복 접속 시 정책 이관은 멱등적이어야 함.
- 동기화로 이전 정책 계획이 도착하면 진행 증거를 우선 보존. 최신 필드라는 이유만으로 통째로 덮어쓰지 않음.

### A5. 최소 UI 변경

- 제출 전: “퀴즈 제출”
- 기기 저장 중: “답안을 저장하고 있어요”
- 저장 성공: “저장했어요” + “다음 과목”
- 서버 미전송: “이 기기에 저장됨 · 서버 전송 대기”
- 저장 실패: “저장하지 못했어요. 답안은 유지 중이에요” + “다시 저장”
- 전체 완료: “8/8 활동 완료”
- 시간: “예상 45분 · 실제 학습 42분” 등 완료 수와 별도 표시

“8/8 완료, 시간 42/45분”이면 완료를 취소하거나 3분을 강제로 더 기다리게 하지 않는다.
가장 눈에 띄는 버튼은 현재 상태에서 실행 가능한 다음 행동 1개로 유지한다.

## 5. 작업 B: 일요일 복습의 결정적 구성

### B1. 선택 정책

최대 10문항, 기본 공개 모의고사 6 + 주중 오답 4.
부족한 쪽은 다른 쪽으로 채우며, 전체 후보가 적으면 실제 개수만 출제한다.
중복으로 10개를 채우지 않는다.

후보 조건:
- 현재 학습자, 한국 시간 해당 주 월요일 00:00부터 현재까지.
- 주중: 실제 제출 완료된 일반 퀴즈의 최초 오답.
- 시험: 공개 확인된 해당 주 모의고사의 최초 오답.
- 원문·정답·선택지/허용 답안·지문을 확인할 수 있는 문항.
- 부정확/폐기/검수 보류 문항 제외.
- 검수 보류 제외 수는 진단에 남기되 학생에게 정답을 노출하지 않음.

각 출처 안의 순서:
1. 같은 개념의 반복 오답 횟수 내림차순.
2. 최근 오답 시각 내림차순.
3. 안정적인 문항 ID 오름차순.

중복 판단은 질문 문자열만 쓰지 않는다.
과목 + 지문 ID 또는 정규화 지문 해시 + 질문 + 정답 + 범위를 포함한 fingerprint를 사용한다.
동일 질문 문구라도 지문이 다르면 다른 문항이다.
양쪽 출처에서 같은 문항이면 1개만 출제하고 sourceReferences는 둘 다 보존하며 시험 할당에 포함한다.

### B2. 순수 선택 함수와 UI 분리

신규 `weekly-review-policy.js`:
```js
buildCandidates({userId, weekId, reports, publishedExams, now})
selectReview({mockCandidates, weeklyCandidates, limit:10, mockTarget:6})
// {items, counts, excluded, sourceStatus}
```
실제 입출력 형태는 저장 구조를 확인해 고정한다. 외부 원본 배열을 mutate하지 않는다.
`weekly-review.js`는 비동기 로딩·세션 저장·화면에 집중한다.

### B3. 로딩과 시작 시점

상태: loading → ready / fallback_ready / empty / error → in_progress → completed.

- 주중 후보와 서버 시험 목록을 가져온 뒤 시작 전 목록을 구성한다.
- 서버 조회는 유한한 대기 시간(기본 8초, 상수로 관리)을 둔다.
- 응답 지연/실패 시 “시험 기록 확인이 늦어지고 있어요”와 “주중 오답으로 시작”, “다시 확인”.
- loading만으로 빈 복습 세션을 완료 저장하지 않는다.
- 시작 버튼 클릭 전: 늦게 온 공개 시험 오답을 반영 가능.
- 시작 후: 원문·순서·문항 수·현재 답안을 동결. 늦은 응답이 바꾸면 안 됨.
- 일요일 0문항: “복습할 오답이 없어요” 표시. 자동으로 10문항 완료나 점수 생성 금지.
- 전부 제외된 경우에는 “오답 없음”과 “확인 가능한 문제 없음”을 구분한다.
- 미공개 시험이 있으면 “결과 공개 후 시험 오답도 복습할 수 있어요”.

주중 복습을 이미 시작/완료한 뒤 시험이 공개되면:
- 별도 “공개된 시험 오답 복습” 보충 세션 제공.
- 기존 세션의 문항/점수/완료를 변경하지 않음.
- 그 주 최대 6개 미복습 시험 오답, 부족하면 실제 수만.
- 같은 source question을 중복 제출·보상하지 않음.
- 기본 일요일 완료 여부는 유지. 보충은 추가 활동으로 표시.

### B4. 세션 저장과 호환

세션 snapshot에 사용자, 한국 날짜, weekId, policyVersion, sessionId, 출처,
문항 원문·채점 정보, 답안, 현재 위치, startedAt, submittedAt을 저장한다.
비공개 시험 payload는 복습 세션에 넣지 않는다.

기존 `SmartStudy_WeeklyReview_<user>_<date>`는 호환 어댑터로 읽는다.
기존 시작/완료 세션을 새 선택 정책으로 재작성하지 않는다.
보충 세션은 별도 키/ID로 저장하고 weekly-schedule의 기존 완료 판독과 호환시킨다.
재시도는 동일 세션 ID, 새 회차는 다른 ID와 parentSessionId를 사용한다.
현재 preference 경로의 서버 동기화 여부를 확인해 문서화한다.
검증 전에는 “다른 기기에서 복습 이어하기 지원”이라고 보고하지 않는다.

### B5. 주요 파일

`weekly-review.js`, `weekly-review.html`, `weekly-schedule.js`,
`mock-exam-results.js`, `mock-wrong-note.js`, `answer-validation.js`,
`weekly-process.test.js`, `mock-publication.test.js`.
공개 확인은 기존 MockPublication 경로를 사용하고 서버 권한 변경을 끼워 넣지 않는다.

## 6. 작업 C: 문항·채점 정확성

### C1. 검사 수준을 구분

1. 형식: 필수 필드, 정답 인덱스, 선택지 중복, NaN/Infinity.
2. 수학 의미: 조건으로부터 독립 계산한 정답과 일치.
3. 교육적 의미: 정답 유일성, 단위, 조건, 해설·그림 일치.
4. 독해 의미: 지문 근거, 추론 범위, 복수 정답 가능성, 오답 이유.

1번 통과를 2~4번 통과라고 표현하지 않는다.

### C2. 수학 템플릿 인벤토리

기존 `math-quiz-generators.test.js`의 형식 검사를 유지하고 독립 검증을 추가한다.
`Utils.generateMathQuiz()`와 각 수학 데이터 파일, 수학 공식 퀴즈의 실제 생성 경로를 포함한다.

인벤토리 필드:
`templateId`, `generatorId`, 학년/단원/유형, 입력 범위, 정답 형태,
oracle 지원 여부, 경계값, 검수 상태, 실패 seed.

기존 738 템플릿과 생성기 종류 수를 별도로 집계한다.
모든 템플릿을 목록에 포함하되 지원하지 않는 생성기를 통과로 처리하지 않는다.
결과에는 독립 검증 완료 N/전체 M과 미지원 목록을 출력한다.

### C3. 독립 정답 검증기

테스트 전용 `tests/helpers/math-answer-oracles.cjs`와 실행 테스트를 추가한다.
프로젝트 CI는 루트 `*.test.js`를 실행하므로 진입 테스트는 루트에 둔다.

- 프로덕션 정답 생성 함수를 호출해 그 결과를 정답 oracle로 재사용하지 않는다.
- 생성기의 정답/해설을 파싱해서 “독립 정답”으로 쓰지 않는다.
- 입력 피연산자·조건으로부터 별도 계산한다.
- 입력을 얻기 어렵다면 생성 결과에 seed/피연산자 검증 메타데이터를 추가한다.
- 이 메타데이터에 정답 파생값을 넣어 독립성을 무너뜨리지 않는다.
- 한 문장의 한국어를 무리하게 정규식으로 파싱하는 방식을 기본으로 하지 않는다.
- 생성기의 실제 입력과 렌더링된 문제 조건도 일치하는지 별도 확인한다.

우선 검사군:
- 사칙연산, 음수, 소수 비교, 분수 크기·연산.
- 비/비례식/백분율, 식의 값/빈칸, 일차방정식.
- 소인수분해, 약수·배수·최대공약수·최소공배수.
- 길이·둘레·넓이·부피, 도형의 존재 조건, 단위 환산.
- 반올림·근삿값, 정수·실수 해의 구분.
- 수학 공식 퀴즈의 기호 의미·대입 계산·조건.

분수는 정수 분자/분모 및 최대공약수로 비교한다.
부동소수점 오차를 숨기기 위한 무조건 반올림이나 넓은 epsilon은 금지.
근삿값 문항만 문제에 지정된 자리수/오차를 적용한다.
서로 다른 문자열이지만 수학적으로 같은 선택지(1/2, 0.5)도 중복 정답으로 탐지한다.
음수 해 가능 여부, 0으로 나누기, 퇴화 도형, 음수 길이 등을 경계값에 포함한다.

난수는 seed 재현 가능하게 만든다. 전역 Math.random을 다른 테스트에 누출하지 않는다.
PR 기본 검사는 생성기별 고정 seed+경계값, 확장 검사는 여러 seed로 실행한다.
실패 시 templateId/seed/입력/실제 질문/예상 정답/선택지를 출력한다.

### C4. 독해 및 언어 문항 검수

현재 국어 54지문·영어 32지문과 모의고사 독해 bank를 인벤토리로 만든다.
지문 수와 문항 수를 각각 실측한다.
모든 문항은 구조 검사, 의미 검수는 상태별로 명확히 구분한다.

검수 기록:
- 문항 ID/콘텐츠 버전.
- 정답을 뒷받침하는 문장 ID 또는 문장 인용.
- 추론 문제라면 필요한 추론 단계와 과도한 가정이 없는 이유.
- 각 오답이 지문과 맞지 않는 이유.
- 모호한 표현/복수 정답/번역 불일치 여부.
- pass / revise / quarantine / unreviewed.

우선순위: 모의고사 독해 → 신규 추가 지문 → 기존 나머지.
영어 어휘·문법과 한자도 동일 정답이 다른 선택지로 중복되는지 구조 검사를 포함한다.
사실 확인이 필요한 과학·역사 내용은 신뢰할 수 있는 원자료로 확인하고 출처를 검수 기록에 남긴다.
한 번의 AI 검토를 외부 교육 전문가 검수 완료라고 표현하지 않는다.
전량 검수가 끝나지 않으면 검수된 범위와 남은 수를 보고하고 전체 정확성을 보증하지 않는다.

### C5. 오류 문항 처리

- 새 출제 전에 오류가 확정된 문항은 제외하고 같은 과목·범위의 검증된 문항으로 대체.
- 대체 후보가 없으면 문항 수를 명시하거나 시작을 막고 이유 표시. 가짜 문제/중복 채우기 금지.
- 55문항 정식 모의고사는 문항 수를 조용히 줄이지 않음. 기존 부족 처리 유지.
- 진행 중 문제가 발견되면 원문·답안을 보존하고 채점 확인 상태로 분리.
- 이미 완료한 활동을 취소하지 않음.
- 과거 결과는 기존 콘텐츠 버전/문항 snapshot으로 유지.
- 정정 안내는 별도 기록으로 남기고 과거 최초 성적을 덮어쓰지 않음.
- 일요일 복습은 현재 검수된 문항을 사용하되 원본 출처 추적 유지.

`answer-validation.js`의 미확정 응답은 `needs_review`를 유지한다.
영어 부정문·시제·수 일치가 달라지는 답을 과도한 정규화로 정답 처리하지 않는다.
자유 서술은 검증된 acceptedAnswers 또는 명시적인 자기 점검 경로만 사용한다.

## 7. 구현 순서와 중간 완료 기준

### 0단계: 기준 확보
- git status/HEAD/원격 관계 확인, 사용자 미커밋 수정 보존.
- 자동 테스트 기준 실행. 테스트 로그 보관.
- 8과목의 학습→퀴즈→기기 저장→보고서→오늘 완료 호출 지도 작성.
- 과목별 최소 시간 설정 출처 확인.
- 배포/소스 버전이 다르면 분석 기준 명시.

### 1단계: 정책과 데이터 호환
- 시간 단일 정책, 계획 전환, 복습 순수 선택 함수, 문항 인벤토리.
- 순수 함수 테스트 먼저 작성/실행.
- 여기서 UI·저장소 전체 리팩터링하지 않음.

### 2단계: 일일 흐름 연결
- 실제 과목 제출 경계에 저장 확인과 다음 이동 연결.
- 타이머 정책, 상태 API, 관리자 충돌 안내 적용.
- 8과목 각각 정상·낮은 점수·새로고침 검증.

### 3단계: 일요일 흐름 연결
- 공개 목록 로딩/timeout/시작 시 동결/보충 세션/구버전 복원 구현.
- 숨김 시험 유출·늦은 응답·중복 제출 테스트.

### 4단계: 정답 검증과 콘텐츠 수정
- 수학 oracle, seed, 오류 템플릿 수정 및 회귀 사례.
- 독해 근거 검수와 필요한 수정.
- 수정 문항 ID·변경 이유·검증 결과를 별도 감사표로 기록.

### 5단계: 통합 검증 및 인계
- 자동·브라우저 검증, 기록 보존 비교, 검수 커버리지 보고.
- 남은 항목과 배포 가능/보류 사유를 작성.
- 이번 사용자 요청은 계획서 작성이므로 실제 구현/배포를 완료했다고 말하지 않음.
- 구현을 진행하게 되면 배포 승인 범위를 확인하고 승인된 단계에서만 배포한다.

## 9. 완료 판정과 보고

배포 후보 조건:
1. A/B 필수 테스트 전부 통과.
2. 수학 독립 검증 커버리지와 미지원 항목 공개.
3. 새로 수정한 문항은 모두 회귀 검증과 정답 근거 확보.
4. 알려진 정답 오류가 출제 가능한 상태로 남지 않음.
5. 구계획/보고서/오답 최초 데이터 보존 확인.
6. UI에서 완료와 서버 동기화 상태를 혼동하지 않음.
7. 모든 자동 테스트 통과. CRLF 실패는 테스트를 정상화해서 해결하며 assertion 삭제 금지.
8. 실제 미검증 범위 명시.

최종 보고 필드:
- 구현한 정책과 바뀐 파일.
- 자동 테스트 실행 명령/통과 수.
- 브라우저 시나리오 및 실패 복구 결과.
- 수학 템플릿 검증 N/M, 독해 문항 검수 N/M, 보류 목록.
- 기록 보존 결과, 남은 위험.
- 배포 전/배포 완료/실기기 확인을 각각 구분.

배포할 경우 version.json, service-worker 캐시, 변경 스크립트의 HTML 참조를 점검한다.
개인 문서나 scratch를 커밋하지 않는다. 배포 workflow 성공과 실제 배포 버전을 확인한다.
롤백은 이전 코드 배포로 수행하되 새로 저장된 학습 기록을 지우지 않는다.

## 10. GPT-6.1 Sol 실행 지침

> 이 문서를 먼저 읽고 기준 커밋 이후 변경을 확인한다.
> 기능을 한 번에 재작성하지 말고 0→5단계 순서로 진행한다.
> 단계마다 관련 테스트를 통과시킨 후 다음 단계로 이동한다.
> 테스트 편의를 위해 실제 학생 기록·최초 답안·권한·출제 범위를 완화하지 않는다.
> 구체적인 코드가 이 계획의 가정과 다르면 근거와 조정 내용을 기록한다.
> 승인된 목표 안의 구현 세부사항은 스스로 결정하되 학습 정책을 임의로 바꾸지 않는다.
> 불명확한 채점은 정답으로 추정하지 않는다.
> 실패를 같은 방식으로 두 번 반복하면 원인과 로그를 정리하고 접근을 바꾼다.
> 저장/이관/권한 설계의 중대한 변경이 필요할 때만 별도 고난도 검토를 요청한다.
> 모델을 실제로 전환하지 않았다면 GPT-6.1 Sol 또는 Astra로 작업했다고 주장하지 않는다.
> 전역 구조·무료 운영·기존 UI를 유지하며 범위 밖 리팩터링을 끼워 넣지 않는다.

진행 체크포인트는 별도 작업 메모에 현재 커밋, 완료 단계, 실행한 테스트, 남은 문제를 짧게 남긴다.
각 단계 커밋은 독립적으로 검토 가능하게 나누고 최종 검증 전 배포하지 않는다.
